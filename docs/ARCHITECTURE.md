# Архитектура системы мониторинга (рабочее название — Sentinel)

Система для IT-аутсорсинга: единый сервер у нас, агенты у клиентов, дашборд для инженеров.
Документ фиксирует принятые решения. Меняем — правим здесь же.

## 1. Ключевые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Язык | C# везде | Один стек; единственный поддерживаемый вариант для Windows Server 2008 R2 |
| Агент | .NET Framework 4.8, Windows-служба | Работает на 2008 R2 SP1 и выше; полный доступ к WMI, службам, EventLog, VSS, SQL Server |
| Сервер | ASP.NET Core (.NET 10 LTS) в Docker на Linux VPS | Дёшево, стандартно, обновление одной командой |
| Общий код | `Sentinel.Contracts` (netstandard2.0) | Один набор DTO/протокола для агента и сервера |
| БД | PostgreSQL 16 | Надёжно, бесплатно, партиционирование для метрик |
| Дашборд | React + TypeScript (Vite) | Отдельный SPA, обычный web-фронт |
| Канал агент→сервер | HTTPS + SignalR (только исходящее соединение агента) | У клиента ничего не открываем в файрволе |
| 1С | Файловая (.1CD), MS SQL, PostgreSQL | Все три встречаются у клиентов |
| Видео | Универсальный слой ONVIF/RTSP + Hikvision ISAPI + Dahua HTTP API | Зоопарк регистраторов |
| Оповещения | Email, Telegram, Max | Требование заказчика |

## 2. Компоненты

```
┌──────────────── Сеть клиента ────────────────┐
│ Sentinel.Agent (служба Windows, net48)       │
│   ├─ Modules (чекеры): services, disks,      │
│   │   eventlog, backup.*, net.*, cctv.*, …    │
│   ├─ CommandExecutor (перезапуск служб,      │
│   │   ребут, скрипты) — по белому списку     │
│   ├─ LocalStore (офлайн-буфер результатов)   │
│   └─ Transport (HTTPS/SignalR → сервер)      │
└───────────────────────┬──────────────────────┘
                        │ TLS 1.2+, токен агента, pinning сертификата сервера,
                        │ команды подписаны ключом сервера
┌───────────────────────▼──────────────────────┐
│ Sentinel.Server (ASP.NET Core, Docker)       │
│   ├─ Agent API + AgentHub (SignalR)          │
│   ├─ Rules/Alerting engine                   │
│   ├─ Scheduler (retention, escalation, …)    │
│   ├─ Notifications (Email/Telegram/Max)      │
│   ├─ Web API для дашборда (JWT, RBAC, 2FA)   │
│   └─ PostgreSQL                              │
├──────────────────────────────────────────────┤
│ Sentinel.Web (React SPA) — дашборд           │
└──────────────────────────────────────────────┘
```

### 2.1 Агент

- Один exe, ставится как служба `SentinelAgent` (LocalSystem). Инсталлятор — MSI (WiX) с параметрами: адрес сервера, enrollment-токен.
- **Никаких входящих портов.** Агент сам подключается к серверу, держит SignalR-канал (WebSocket; на 2008 R2 — автоматический fallback на SSE/long-polling, т.к. там нет `ClientWebSocket`).
- **Конфигурация приходит с сервера.** Локально хранится только: адрес сервера, токен агента (зашифрован DPAPI, LocalMachine), pin сертификата, последний полученный конфиг (для работы офлайн).
- **Модули** — независимые чекеры с единым интерфейсом:
  ```csharp
  interface IModule {
      string Id { get; }                       // "services", "disks", "backup.mssql"
      Task<CheckResult[]> RunAsync(ModuleConfig cfg, CancellationToken ct);
  }
  ```
  Каждый модуль имеет JSON-схему конфигурации. Дашборд рисует форму настройки по схеме → «выбор функционала под клиента» = включить модуль и заполнить параметры.
- **Планировщик** внутри агента: у каждого экземпляра модуля свой интервал/cron.
- **Офлайн-буфер**: результаты пишутся в локальную SQLite-очередь и досылаются при восстановлении связи. Бэкапы выполняются по локальному расписанию даже без связи с сервером.
- **Команды**: сервер шлёт `Command{Id, Type, Payload, IssuedAt, Signature}`. Агент проверяет подпись (Ed25519, публичный ключ сервера зашит в конфиг при enrollment), проверяет, что тип команды разрешён в локальной политике, выполняет, отправляет `CommandResult`. Каждое действие — в локальный лог и на сервер.
- **Самообновление**: сервер публикует новую версию с подписью; агент скачивает, проверяет подпись, обновляется через вспомогательный процесс.

### 2.2 Сервер

- ASP.NET Core Minimal API + SignalR-хаб для агентов.
- Слои: `Server` (хосты/API) → `Core` (домен: правила, инциденты, планировщик) → `Data` (EF Core, PostgreSQL). `Notifications` — отдельный проект с провайдерами каналов.
- **Rules/Alerting engine**: каждый `CheckResult` проходит через правила → меняет состояние `Check` (OK/WARN/CRIT/UNKNOWN) → при переходе состояния открывается/закрывается `Incident` → маршрутизация в каналы с учётом дедупликации, антифлаппинга, окон обслуживания, эскалации.
- Пропажа хартбита агента (нет связи N минут) — тоже инцидент.
- Фоновые задачи: ретеншн метрик, эскалация неподтверждённых инцидентов, проверка «бэкап не пришёл вовремя» (dead man's switch — важно: агент может молчать именно потому, что всё сломалось).

### 2.3 Дашборд

Страницы: Обзор (все клиенты, светофор) → Клиент → Хост → Проверки; Инциденты (лента, подтверждение, комментарии); Бэкапы (матрица «клиент × база × последний успешный»); Видеонаблюдение (регистраторы, каналы, дрейф времени); Команды и аудит; Настройки (пользователи, роли, каналы оповещений, шаблоны конфигураций).

Конфигуратор агента — форма по JSON-схемам модулей + «шаблоны» (например, «Типовой сервер 1С»), которые применяются к хосту и затем дорабатываются.

## 3. Безопасность

1. **Транспорт**: только TLS 1.2+ (на 2008 R2 инсталлятор включает TLS 1.2 в реестре и ставит требуемые KB). Агент делает pinning SHA-256 публичного ключа сервера — корпоративный MITM-прокси не пройдёт.
2. **Enrollment**: инженер создаёт в дашборде одноразовый токен для конкретного клиента/хоста (TTL 24 ч). Агент предъявляет его один раз → получает постоянный `AgentId` + секрет. Секрет хранится в DPAPI.
3. **Аутентификация агента**: Bearer-секрет по TLS + HMAC-подпись тела с timestamp/nonce (защита от replay).
4. **Команды подписаны** приватным ключом сервера (Ed25519). Даже компрометация БД/канала не даёт выполнить команду без ключа подписи (хранится отдельно, в секрете контейнера).
5. **Белый список команд** на стороне агента — задаётся при установке и не меняется удалённо (например, клиент может запретить ребут).
6. **Пользователи**: пароль (Argon2) + TOTP 2FA обязательна для ролей с правом выполнять команды. JWT с коротким TTL + refresh. RBAC: `Admin`, `Engineer`, `ReadOnly`, `ClientViewer` (видит только свой тенант).
7. **Аудит**: любое действие пользователя (команда, изменение конфига, ack инцидента) и агента (выполнение команды) — в неизменяемый `AuditLog`.
8. **Секреты в конфигах модулей** (пароли SQL, регистраторов, SMTP) шифруются на сервере (AES-GCM, ключ из секрета контейнера), агенту передаются только по TLS, на агенте — DPAPI.
9. **Минимум привилегий**: агент работает под LocalSystem только потому, что нужны VSS и управление службами; при желании можно указать отдельную учётку.

## 4. Модель данных (основное)

```
Tenant (клиент) ─┬─ Site (площадка/офис) ─── Host (сервер/ПК/регистратор)
                 │                              └─ Agent (для хостов с агентом)
                 │                              └─ Check (экземпляр модуля + конфиг + состояние)
                 │                                    ├─ CheckResult (история статусов)
                 │                                    └─ Metric (числовые ряды, партиции по времени)
                 ├─ Incident (открыт/подтверждён/закрыт, severity, история)
                 ├─ NotificationChannel (email/telegram/max + маршруты)
                 ├─ BackupJob / BackupRun (что, куда, когда, размер, проверка)
                 │    └─ BackupArtifact (локальная копия / облачная копия, хеш, статус)
                 ├─ CloudAccount (Яндекс.Диск / S3: токен, квота, последняя проверка)
                 └─ CctvDevice / CctvChannel
User, Role, ApiToken, EnrollmentToken, Command (очередь + результат), AuditLog,
AgentConfigVersion (история конфигов), AgentRelease (обновления агента)
```

Метрики — таблица `metrics(time, check_id, name, value)` с партициями по месяцу и ретеншном (по умолчанию 90 дней сырых данных). TimescaleDB — опция позже, если понадобится.

## 5. Модули агента (функционал под клиента)

| Модуль | Что делает | Команды |
|---|---|---|
| `system` | CPU, RAM, аптайм, pending reboot, версия ОС, время (дрейф от сервера) | `reboot`, `shutdown` |
| `services` | Состояние выбранных служб Windows, автоперезапуск (опция) | `service.start/stop/restart` |
| `disks` | Свободное место (порог в % и ГБ), позже SMART | — |
| `eventlog` | Фильтр по журналу/источнику/уровню/EventID/тексту, дедупликация | — |
| `net.ping` | Доступность хостов в сети клиента (ICMP) | — |
| `net.tcp` | Проверка порта, опционально TLS-рукопожатие и срок сертификата | — |
| `backup.files` | Полный/разностный (по mtime и archive-бит) в zip/папку, ретеншн, проверка | `backup.run` |
| `backup.1c.file` | VSS-снапшот → копия `.1CD` + внешние обработки; ретеншн; тестовое открытие | `backup.run` |
| `backup.mssql` | `BACKUP DATABASE` full/diff/log, `RESTORE VERIFYONLY`, копирование в цель, ретеншн | `backup.run` |
| `backup.postgres` | `pg_dump` (custom format), проверка, ретеншн | `backup.run` |
| `cctv.onvif` | Доступность, `GetSystemDateAndTime` (дрейф времени), список каналов | `cctv.settime` |
| `cctv.rtsp` | Проверка потока каналов (DESCRIBE + первые кадры через ffprobe) | — |
| `cctv.hikvision` | ISAPI: статус записи по каналам, HDD, время, потеря видео | `cctv.settime`, `cctv.reboot` |
| `cctv.dahua` | HTTP API: аналогично | `cctv.settime`, `cctv.reboot` |
| `backup.cloud` | Выгрузка готовых бэкапов в облако (Яндекс.Диск, S3), контроль наличия и целостности в облаке, ретеншн в облаке, квота диска | `backup.cloud.sync`, `backup.cloud.verify` |
| `remote.exec` | Выполнение PowerShell-скрипта, подписанного сервером | `exec` |

Цели для бэкапов: локальная папка, SMB-шара, **Яндекс.Диск** (основное облако), S3-совместимое хранилище, позже WebDAV.

### 5.1 Облачные бэкапы (Яндекс.Диск)

Облако — отдельный слой поверх локальных бэкапов, а не замена: любой модуль `backup.*` создаёт артефакт локально, затем `backup.cloud` выгружает его в облако и следит за ним.

- **API**: REST Яндекс.Диска (`cloud-api.yandex.net/v1/disk`) по OAuth-токену приложения. WebDAV не используем — медленнее и без метаданных. Токен хранится как секрет конфига (шифруется на сервере, DPAPI на агенте).
- **Выгрузка**: загрузка по ссылке из `/resources/upload` с докачкой; после загрузки сверяем `md5`/`sha256` из метаданных Диска с локальным хешем — только тогда выгрузка считается успешной.
- **Структура в облаке**: `/Sentinel/<клиент>/<хост>/<задание>/<yyyy-MM-dd_HHmm>_<имя>.zip`. Для разностных бэкапов — папка полного бэкапа + цепочка разностных.
- **Контроль** (по расписанию, независимо от выгрузки): список файлов в облаке, дата и размер последнего, сравнение с ожидаемым расписанием → инцидент «в облаке нет свежего бэкапа», квота Диска (свободно < порога → WARN), несовпадение хеша → CRIT.
- **Ретеншн в облаке**: отдельные правила (обычно длиннее локальных, например 3 локальных + 30 в облаке или GFS). Удаление — в корзину Диска с последующей очисткой, чтобы был шанс отката.
- **Ограничения**: пропускная способность (лимит скорости выгрузки в рабочие часы), окно выгрузки (например, только ночью), максимальный размер файла (разбиение на тома при необходимости).
- На сервере страница «Бэкапы» показывает обе колонки: локальный и облачный статус по каждой базе.

Общие для всех бэкапов: расписание, ретеншн (N последних / N дней / GFS), лог каждого запуска, размер, длительность, отправка результата и **обязательный инцидент, если бэкап не пришёл вовремя**.

## 6. Оповещения

- Каналы: SMTP, Telegram Bot API, Max Bot API.
- Маршруты: `Tenant × Severity × Канал × Расписание (тихие часы)`. Эскалация: не подтверждён за N минут → следующий уровень.
- Дедупликация: один инцидент — одно уведомление об открытии + одно о закрытии (+ напоминания по настройке). Антифлаппинг: состояние должно продержаться K проверок.
- Окна обслуживания: на время планового ребута инциденты подавляются.

## 8. Протокол агент ↔ сервер (кратко)

- `POST /api/agent/enroll` — enrollment-токен → `{agentId, secret, serverPublicKey, certPin}`.
- `GET  /api/agent/config` — актуальный конфиг (ETag по версии).
- `POST /api/agent/results` — батч `CheckResult[]` + метрики (сжатие gzip).
- `POST /api/agent/backup-runs` — результаты бэкапов с логом.
- SignalR `/hubs/agent`: сервер → `Command`, агент → `CommandResult`, `Heartbeat` каждые 30 с, `ConfigChanged` (агент перечитывает конфиг).
- Все ответы сервера и все команды — с подписью; все запросы агента — с HMAC.

Подробности — в `docs/PROTOCOL.md` (появится вместе с реализацией контрактов).
