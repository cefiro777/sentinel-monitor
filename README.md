# Sentinel — мониторинг серверов клиентов для IT-аутсорсинга

[![CI](https://github.com/cefiro777/sentinel-monitor/actions/workflows/ci.yml/badge.svg)](https://github.com/cefiro777/sentinel-monitor/actions/workflows/ci.yml)
[![Release](https://img.shields.io/github/v/release/cefiro777/sentinel-monitor)](https://github.com/cefiro777/sentinel-monitor/releases/latest)
[![License: AGPL-3.0](https://img.shields.io/badge/license-AGPL--3.0-blue)](LICENSE)

Один сервер мониторинга на всех клиентов: агент на Windows-серверах клиента сам выходит на связь (входящие порты у клиента не нужны),
сервер копит состояние, открывает инциденты и присылает оповещения в Telegram, Max и на почту.

- **Серверы Windows 2008 R2 SP1 — 2025**: CPU, память, диски, службы (с автоперезапуском), журналы событий с подсказками по частым ошибкам, аптайм, часы, ожидающая перезагрузка.
- **Бэкапы**: файлы (zip-наборы или зеркало с отложенным удалением, длинные пути), 1С (файловые базы), MS SQL, PostgreSQL; выгрузка в Яндекс.Диск; контроль просрочки на сервере.
- **Видеонаблюдение**: Hikvision, Dahua, ONVIF, RTSP — каналы, **наличие записи**, диски, расхождение часов; выставление времени и перезагрузка регистратора.
- **Hyper-V**: состояние ВМ, heartbeat гостевой ОС, старые контрольные точки, репликация.
- **Сеть**: ping, TCP-порты, HTTP(S) и сертификаты.
- **Инциденты**: антифлаппинг, задержка оповещения (кратковременные пики не будят), «в работу» на срок, напоминания, тихие часы, окна обслуживания.
- **Удобство**: шаблоны проверок по ролям серверов, скрытие отдельных показателей, графики за 24 ч, удалённые действия (перезапуск службы, запуск бэкапа) с 2FA и белым списком на агенте, автообновление агентов с проверкой подписи.
- **Мультиклиентность**: клиенты, роли (админ / инженер / клиент — только свои серверы), аудит.

## Установка

Готовые сборки — на странице [релизов](https://github.com/cefiro777/sentinel-monitor/releases/latest).

### Сервер на Linux (рекомендуется)

Ubuntu 22.04+ / Debian 12+, 2 vCPU, 2 ГБ RAM. Docker ставится автоматически, скрипт спросит режим и домен:

```bash
curl -fsSL https://raw.githubusercontent.com/cefiro777/sentinel-monitor/main/deploy/install.sh | sudo bash
```

- **domain** — свой домен, HTTPS от Let's Encrypt (нужны открытые 80/443);
- **ip** — без домена, HTTPS с внутренним сертификатом (агенты доверяют ему по отпечатку);
- **nginx** — на сервере уже есть nginx/Apache: Sentinel слушает локальный порт, пример конфига прилагается.

В конце скрипт покажет адрес и пароль администратора. Обновление — та же команда. Подробности: [docs/DEPLOY.md](docs/DEPLOY.md).

### Сервер на Windows

`SentinelServer-Setup-x.y.z.exe` — для Windows Server 2016+ / Windows 10+, без Docker и без интернета: внутри PostgreSQL 16, Visual C++ Redistributable и сам сервер.
Установщик спросит адрес и порт, поднимет службы `SentinelPostgreSQL` и `SentinelServer`, откроет порт в брандмауэре, настроит ежедневный бэкап
и покажет пароль администратора. Данные — в `%ProgramData%\Sentinel`, они переживают обновление и удаление программы.

### Агент на серверах клиентов

В дашборде: **«Установка агентов» → клиент → «Создать токен»** — появится команда для PowerShell от администратора.
Для площадок без интернета, со старыми серверами или для установки через GPO/RMM — офлайн-установщик `SentinelAgent-Setup-x.y.z.exe`
(внутри .NET Framework 4.8, ставится при необходимости):

```
SentinelAgent-Setup.exe /VERYSILENT /SERVER=https://monitor.example.com /TOKEN=<токен>
```

Пакет `SentinelAgent-x.y.z.zip` из релиза загрузите в дашборде («Установка агентов» → «Дистрибутив агента») — установленные агенты обновятся сами.

## Разработка

- Архитектура и принятые решения: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)
- План работ: [docs/ROADMAP.md](docs/ROADMAP.md)

Нужны: .NET SDK 10.x и .NET Framework 4.8 Developer Pack (агент), Node.js 20+, Docker Desktop (PostgreSQL).

```bash
# 1. PostgreSQL
docker compose -f deploy/docker-compose.dev.yml up -d

# 2. Сборка всего
dotnet build

# 3. Дашборд → wwwroot сервера (или npm run dev для hot-reload на :5173 с прокси в API)
cd src/Sentinel.Web && npm install && npm run build:server && cd ../..

# 4. Сервер (миграции применяются автоматически; пароль админа — в data/initial-admin-password.txt)
dotnet run --project src/Sentinel.Server
```

Дашборд: http://localhost:5080, логин `admin@local`.

Установщики для Windows собирает `installers\build.ps1` (нужен Inno Setup 6; .NET 4.8, VC++ и PostgreSQL он скачает сам).
Релиз: `git tag v0.4.1 && git push origin v0.4.1` — GitHub Actions соберёт образ сервера в ghcr.io, установщики и пакет агента.

## Агент

Дистрибутив собирается скриптом и публикуется на сервере (страница «Установка агентов», только админ):

```bash
.\deployuild-agent.ps1 -Version 0.2.0     # -> artifacts/SentinelAgent-0.2.0.zip
```

Сервер подписывает пакет своим Ed25519-ключом. Агенты проверяют подпись и обновляются сами раз в сутки (или по кнопке «Обновить агент»).
Установка на сервере клиента — одной командой из дашборда (PowerShell от администратора), либо вручную:

```bash
SentinelAgent.exe enroll --server https://monitor.example.com --token <token> --allow ping,config.refresh,agent.update,service.*,backup.*,cctv.*
SentinelAgent.exe install

# Отладка в консоли без службы:
SentinelAgent.exe run
```

Диагностика связи: `SentinelAgent.exe diag` (DNS, TCP, прокси, HTTPS, подписанный запрос). Если у учётки службы (LocalSystem) прописан
недоступный прокси — `SentinelAgent.exe proxy none` (или `proxy http://адрес:порт`, `proxy system`); настройка хранится в agent.json.
Белый список команд меняется только на самом сервере: `SentinelAgent.exe allow` (показать), `allow add agent.update`, `allow remove exec`.

Файлы агента: `%ProgramData%\Sentinel\Agent` (agent.json с секретом под DPAPI, кэш конфига, офлайн-буфер SQLite, логи).

## Виртуальные машины

Проверка `vm.hyperv` ставится на сам хост Hyper-V: агент читает WMI `rootirtualization2` — агенты внутри гостевых ОС и отдельные учётки не нужны.
Контролируются: состояние каждой ВМ (с учётом списка «должны быть выключены»), аптайм, службы интеграции (heartbeat — признак зависшей гостевой ОС),
контрольные точки старше N дней (растёт разностный диск) и состояние репликации Hyper-V, если она настроена.

## Бэкапы и Яндекс.Диск

Задание `backup.files` работает в двух режимах: **архивы zip** (полный раз в N дней + разностные, ретеншн наборов, выгрузка в облако) и
**зеркало** — актуальная копия папки в назначении: копируются только изменившиеся файлы, при желании удаляется то, чего больше нет в источнике (аналог `robocopy /MIR`).
Пути длиннее 260 символов копируются через Win32 (`\?\`), так что глубокие файловые шары переносятся целиком и на Server 2008 R2.
Непереносимые файлы (нет прав, файл занят) можно пропускать: задание остаётся успешным, а такие файлы попадают в скрытый журнал `.sentinel-mirror-skip.tsv` в копии и больше не пробуются, пока не изменятся в источнике.
Файл, пропавший из источника, удаляется из копии не сразу, а через заданное число дней (по умолчанию 14) — есть время заметить случайное удаление и забрать файл из копии;
отметки хранятся в скрытом `.sentinel-mirror.tsv` в папке копии. Зеркало — для больших рабочих папок, где нужна свежая копия, а не история версий;
защиты от шифровальщика оно не даёт, для этого держите рядом zip-задание.

Задания бэкапа — это проверки типов `backup.files`, `backup.1c.file`, `backup.mssql`, `backup.postgres` на странице хоста. Агент запускает их по расписанию,
складывает артефакты в папку/шару, проверяет, чистит старые наборы и при включённом облаке выгружает в Яндекс.Диск с проверкой хеша.

Токен Яндекс.Диска: на https://oauth.yandex.ru создайте приложение с правами «Яндекс.Диск REST API» (`cloud_api:disk.read`, `disk.write`, `disk.info`),
откройте `https://oauth.yandex.ru/authorize?response_type=token&client_id=<ID>` под нужным аккаунтом и вставьте `access_token` в настройки задания.
Файлы ложатся в `/Sentinel/<клиент>/<хост>/<задание>/`. Токен хранится в БД зашифрованным и передаётся только агенту.

Если по заданию нет успешного бэкапа дольше 1.5 периода расписания — сервер сам открывает инцидент «бэкап просрочен», даже если агент молчит.

## Шаблоны проверок

Страница «Шаблоны»: набор проверок (с теми же формами, что на хосте), который применяется к нескольким серверам клиента разом — галочками.
Проверка на хосте считается той же при совпадении модуля и названия: такие пропускаются или (режим «перезаписывать») перенастраиваются по шаблону, остальные проверки хоста не трогаются.
При первом запуске сервер создаёт встроенные шаблоны по ролям (базовый сервер, контроллер домена, терминальный, MS SQL, 1С, файловый/печать, Hyper-V) — их можно править и удалять.
В форме «Службы Windows» есть готовые наборы служб по ролям (`src/Sentinel.Server/Seed/service-presets.json`) — кнопка «Добавить набор».
Шаблон бывает общим или только для одного клиента; готовый набор с настроенного сервера снимается кнопкой «Сохранить как шаблон» на странице хоста (секреты остаются зашифрованными).

## Видеонаблюдение

Проверки `cctv.hikvision` (ISAPI), `cctv.dahua` (CGI), `cctv.onvif` (любой вендор) и `cctv.rtsp` (конкретные потоки) добавляются на хост, у которого есть сетевой доступ
к регистраторам. Контролируются: доступность, расхождение часов, состояние дисков, каналы онлайн, **наличие записи за последние N минут** (Hikvision/Dahua) и живость
RTSP-потоков (реальные RTP-данные, не просто открытый порт). Режим каждого канала (проверять / только доступность для записи по движению / игнорировать) задаётся на странице «Видеонаблюдение» в карточке регистратора; есть автовыставление времени по часам сервера. Со страницы «Видеонаблюдение» можно выставить время и перезагрузить регистратор (нужна 2FA).

## Эксплуатация сервера

Linux: `deploy/install.sh` (или вручную: `deploy/docker-compose.yml` — PostgreSQL + сервер + Caddy, `deploy/env.example` → `deploy/.env`). Windows: установщик, см. выше.

Ключи сервера (`/data/keys`): `data.key` (шифрование секретов в БД), `jwt.key`, `signing.key` (подпись команд и пакетов агента). **Потеря `signing.key` или `data.key` = переустановка всех агентов.**
Ежесуточный бэкап (дамп БД + ключи, 14 копий): Linux — сервис `backup` в compose, `deploy/data/backups`; Windows — задача «Sentinel Server Backup», `%ProgramData%\Sentinel\Serverackups`. Забирайте эту папку наружу.

Инциденты: «Принять» — подтверждение, «В работу…» (4 ч / сутки / 3 дня / неделя) — уведомления по инциденту молчат до срока, по истечении срока инцидент снова открывается и оповещает.

Эксплуатация: тихие часы и напоминания о неподтверждённых инцидентах — в маршрутах оповещений; окна обслуживания — на странице хоста (+1/+4/+12 ч);
сроки хранения истории — секция `Sentinel:Retention` в appsettings (метрики 90 дн., инциденты 365 дн. и т.д.).

## Структура

```
src/Sentinel.Contracts      протокол агент ↔ сервер (netstandard2.0)
src/Sentinel.Agent          служба Windows (net48): модули, планировщик, буфер, команды
src/Sentinel.Server.Core    домен
src/Sentinel.Server.Data    EF Core + PostgreSQL, миграции
src/Sentinel.Server         API, SignalR-хаб, безопасность, фоновые задачи
src/Sentinel.Notifications  Email / Telegram / Max
src/Sentinel.Web            дашборд React + TypeScript
tests/                      xUnit
deploy/                     Docker, Caddy, install.sh
installers/                 установщики Windows (Inno Setup): агент офлайн, сервер
```

Миграции: `dotnet ef migrations add <Name> --project src/Sentinel.Server.Data --startup-project src/Sentinel.Server`.
